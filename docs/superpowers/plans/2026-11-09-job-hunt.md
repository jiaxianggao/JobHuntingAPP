# Job Hunt Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans for native execution or superpowers:subagent-driven-development if the user chooses delegated execution. Steps use checkbox syntax for tracking.

**Goal:** Build a personal job application tracker that runs offline on a Windows PC and keeps each role's records and documents across restarts.

**Architecture:** A small Python process serves the browser interface and a JSON API on `127.0.0.1:8765`. A single SQLite database in `%LOCALAPPDATA%\JobHunt\job-hunt.sqlite3` stores roles and attachment bytes. Both pages read the same records through the API.

**Tech stack:** Python 3.12, standard-library HTTP and SQLite modules, plain HTML, CSS and JavaScript, and Python `unittest`. Python is a one-time prerequisite. The app has no package installation step and uses no remote assets.

**Spec:** [PRD.md](../../../PRD.md)

## Global constraints

- Open in a desktop browser on Windows, work offline, and require no login.
- Start on **Calendar**. Keep **Job Applications**, **Not submitted**, **Submitted**, **Add role**, **Mark submitted**, and **Today** as the agreed labels.
- Store one CV and one cover letter copy per role. Allow roles to be saved and submitted before documents are attached.
- Leave cloud storage or sync, online deployment, mobile, a separate Today Plan, and additional hiring stages outside this version. Backup and recovery remain pending a scope decision.
- Use sample data during development. Run automated tests against temporary databases and an ephemeral local port.

## Proposed implementation defaults

- Use a double-click Windows launcher. Launching again opens the existing instance if it is Job Hunt. Closing the browser tab leaves the local process running, and reopening the app after a PC restart uses the same database.
- Use a 25 MiB limit per attachment and display the limit in the upload UI. Save a file only after receiving it in full. Serve copies as downloads so the user can open them in the appropriate desktop application.
- Store submission dates as local calendar dates in `YYYY-MM-DD` form. Accept today or an earlier date. Use a Monday-first calendar and show the current month on launch.

## Review focus

- A second browser tab submits the same role on a different date. The first confirmed date survives and the second tab reloads the current record. Task 3.
- A late-night submission occurs while the date in UTC differs from the PC's local date. The visible date follows the PC. Task 3.
- An attachment upload ends early or exceeds the size limit. Any existing saved copy survives. Task 4.
- Two different roles attach files with the same name. Both copies retain their original bytes. Task 4.
- Another program already uses the launcher port, or a web page attempts to send requests to the local app. The launcher reports the conflict, and the server rejects untrusted requests. Tasks 1 and 5.

## Task 1 — Launch an empty tracker with durable storage

**Files** `server.py`, `storage.py`, `web/index.html`, `web/styles.css`, `tests/test_server.py`, `tests/test_storage.py`.

**Interfaces** `storage.initialize(db_path: Path) -> None`; `server.create_server(db_path: Path, port: int) -> ThreadingHTTPServer`. Routes `GET /` and `GET /api/health`, with health returning `{"app":"job-hunt"}`.

- [ ] Add tests `test_home_opens_calendar`, `test_database_reopens`, and `test_untrusted_host_and_origin_rejected`. Assert that Calendar is initially visible, initializing twice keeps existing database content, and mismatched hosts or cross-origin mutations receive HTTP 403.
- [ ] Run `py -3.12 -m unittest discover -s tests -v` and confirm the new checks fail before implementation.
- [ ] Create the app shell and schema. Use integer role IDs, required company name/type/title, and a nullable submission date as the source of status. Create an attachment table keyed by role ID and attachment kind, with original filename and bytes. Enable foreign keys for each connection.
- [ ] Bind to loopback and check the exact Host header. Require a matching Origin for browser mutations, omit CORS permissions, and serve only known asset paths. Surface initialization failures without substituting a new empty database.
- [ ] Run the tests again. Open the app at `http://127.0.0.1:8765` with the PC offline and verify the empty Calendar and navigation render.

## Task 2 — Create and edit applications on the board

**Files** `storage.py`, `server.py`, `web/index.html`, `web/styles.css`, `web/app.js`, `tests/test_storage.py`, `tests/test_server.py`.

**Interfaces** `GET /api/roles`, `GET /api/roles/{id}`, `POST /api/roles`, `PATCH /api/roles/{id}`. Create and edit accept `company_name`, `company_type`, and `role_title`. Return a role with those fields, `id`, and `submitted_on` as an ISO date or null. Use HTTP 201 for create, 200 for read/edit, 400 for invalid fields, and 404 for unknown IDs.

- [ ] Add failing tests `test_create_and_edit_role` and `test_blank_fields_leave_record_unchanged`. Assert that creating a role returns a stable ID and null submission date, edits survive a database reopen, and a whitespace-only field leaves the prior record intact.
- [ ] Run the test suite and confirm the new cases fail.
- [ ] Implement the role routes with parameterized queries and trimmed, required fields. Render user-entered text as text in the browser. Show API errors in the form and keep the user's input available for retry.
- [ ] Build the two board columns, **Add role**, and the shared details dialog with edit controls. Render a role under **Not submitted** when its date is null.
- [ ] Run the suite. In the browser, add and edit a role, reopen its details, and refresh the page to check that the saved changes remain.

## Task 3 — Submit a role and show it on the calendar

**Files** `storage.py`, `server.py`, `web/index.html`, `web/styles.css`, `web/app.js`, `web/dates.js`, `tests/test_storage.py`, `tests/test_server.py`.

**Interfaces** `POST /api/roles/{id}/submit` accepts `{"submitted_on":"YYYY-MM-DD"}` and returns the updated role. An identical retry returns the current role. A conflicting date returns HTTP 409. `localDateKey(date: Date): string` uses local date fields.

- [ ] Add failing tests `test_submit_with_valid_date`, `test_invalid_or_future_date_preserves_draft`, and `test_repeat_submission_preserves_first_date`. Check a valid past date, an impossible date such as `2026-02-30`, a date after the PC's today, an identical retry, and a conflicting retry.
- [ ] Run the suite and confirm the new cases fail.
- [ ] Validate calendar dates server-side. Record the first submission in a transaction that updates only a draft. If a conflicting write arrives, reload the record and show its saved date.
- [ ] Build the submission dialog with **Today**, a calendar date input, **Cancel**, and **Confirm**. Save only on confirmation. Use local date components for **Today** and avoid converting stored date strings to UTC timestamps.
- [ ] Build the month grid and previous/next controls. Group roles by exact `submitted_on` string and render each as a separate link to the shared details dialog. Refresh board and calendar from the saved response.
- [ ] Run the suite. In the browser, submit two roles on one date, open each from the calendar, cross a month and year boundary, and cancel a third submission. Under a browser timezone that differs from UTC, check **Today** near local midnight against the PC's date.

## Task 4 — Store and open the documents for each role

**Files** `storage.py`, `server.py`, `web/index.html`, `web/app.js`, `tests/test_storage.py`, `tests/test_server.py`.

**Interfaces** `PUT /api/roles/{id}/attachments/{kind}?filename=<encoded-basename>` takes raw file bytes. `GET` on the same path without the query downloads the saved copy. The allowed kinds are `cv` and `cover_letter`. Role responses now include `attachments`, an object keyed by kind with filename values for saved files.

- [ ] Add failing tests `test_same_filename_stays_separate_by_role`, `test_attachments_survive_reopen`, and `test_rejected_upload_preserves_existing_copy`. Compare exact file bytes and names, check interrupted and oversize requests, and confirm an invalid kind is rejected.
- [ ] Run the suite and confirm the new cases fail.
- [ ] Enforce the byte limit before reading and apply a socket read timeout. Reject empty or incomplete uploads. Validate filenames for safe display and response headers. Save or replace the bytes and filename together in one transaction. Return HTTP 413 for oversize uploads and 404 for a missing role or attachment.
- [ ] Serve copies with a safe attachment filename and `application/octet-stream`. Add two independent file controls and actions to open the saved copies. Update each displayed filename after its upload succeeds.
- [ ] Run the suite. In the browser, upload different documents to two roles, move the original files, and open all four saved copies. Check a filename with spaces and accented characters.

## Task 5 — Make startup repeatable and run acceptance

**Files** `start-job-hunt.cmd`, `launcher.py`, `tests/test_launcher.py`, `README.md`.

**Interfaces** `launcher.main() -> int`. Default database path is relative to `LOCALAPPDATA`, regardless of the working directory. Start a new server before opening the browser, or open the browser against an already-running instance with the expected health response.

- [ ] Add failing tests `test_data_path_independent_of_working_directory` and `test_foreign_service_on_port_reports_conflict`. Verify a changed working directory produces the same data path and that an unrelated listener does not launch a browser tab.
- [ ] Run the suite and confirm the new cases fail.
- [ ] Implement double-click startup. Resolve paths relative to the launcher and Windows user data directory. Show a readable error for a missing Python runtime, occupied port, or inaccessible database folder.
- [ ] Document the one-time Python prerequisite, starting and stopping Job Hunt, the local data location, and the full acceptance walkthrough in PRD §10.
- [ ] Run `py -3.12 -m unittest discover -s tests -v`. Run the PRD walkthrough in a Windows desktop browser with a test dataset. Disconnect the network, fully restart Windows, double-click the launcher, and verify the roles, dates, and all saved documents. Record the browser used and the outcome of each acceptance item.

## Delivery checkpoints

- Tasks 1–2 produce an offline tracker that saves and edits drafts.
- Task 3 connects submission, the board, and the calendar.
- Tasks 4–5 complete document retention and everyday Windows startup.

Review each checkpoint before moving on. If version control is available during implementation, keep one focused commit per passing task.
